No inference prompt, external MCP server, model credential, or native permission answer is sent. Reports omit session IDs, private histories and stderr.
- Codex: initialize → initialized → thread/start succeeds; thread/resume of this untouched empty thread returns `no rollout found`. This narrow failure does not prove persisted conversational threads cannot resume.
- DSH: initialize → session/new → session/close → session/list → session/resume → session/close succeeds. Resume accepts the original ID; its response does not return another sessionId. ## Native harness control with deterministic local inference

`pnpm probe:codex:fixture`, `pnpm probe:dsh:fixture` and `pnpm probe:zcode:fixture` start only their own installed stdio harness processes, disposable homes and loopback HTTP fixtures. Inference response bytes are fixed by the test scripts, not generated by a paid/external provider. They are separate optional research probes, not dependencies of CI or Gateway implementations.

- [Codex fixture evidence](evidence/codex-fixture-darwin.json): turn/start completes, the native item/agentMessage/delta matches fixture text, a thread with one saved turn resumes, and turn/interrupt terminates a genuinely in-flight held HTTP request as interrupted. The fixture requests a temporary-file command; native item/commandExecution/requestApproval is answered decline, and the marker file does not exist afterward. Resume succeeds after stopping and restarting the App Server process against the same disposable home.
- [DSH fixture evidence](evidence/dsh-fixture-darwin.json): session/prompt completes with end_turn and ACP agent_message_chunk matches fixture text. Closing and restarting the process, then session/resume with the same ID, succeeds. Native session/cancel terminates an in-flight held request as cancelled. A read-only sandbox blocks the temporary-file command; only after that observed native denial does the fixture request the wider workspace-write mode. Native session/request_permission is answered reject_once and the marker does not exist afterward. No permission grant is returned.
- [ZCode fixture evidence](evidence/zcode-fixture-darwin.json): the actual bundled CLI completes session/send, emits model.streaming/text_delta matching the fixture text, and retains that text after the App Server is stopped and restarted. session/stop cancels an in-flight held HTTP request. Under build mode, interaction/requestPermission is answered deny; the temporary marker file is not created. The overall turn still completes successfully afterward, so turn completion alone must not be treated as evidence that a requested tool ran.
- ZCode setup: the provider file follows the [official model-config format](https://github.com/zai-org/ZCode/blob/main/apps/zcode-cli/docs/usage/03-config.md), with a dummy key and a loopback Chat Completions URL. The installed generic model rule requires reasoningLevel=disabled or enabled; the fixture sends disabled explicitly in modelSelection on each session/send. Runtime preferences disable memory, subagents and automatic question resolution. The [mode guide](https://github.com/zai-org/ZCode/blob/main/apps/zcode-cli/docs/usage/05-permissions.md) distinguishes build (normal write approval) from guarded (ordinary calls may be allowed). An initial guarded-mode temporary write was allowed, consistently with that documented policy; it was not evidence of a failed approval gate.
- These tests validate API control and denial behavior, not production pairing, authenticated human approval, account configuration, real inference quality, or existing-GUI attachment. All commands and marker paths belong to disposable probe directories.

## Desktop application investigation

- ZCode: read application Info.plist (bundle dev.zcode.app, build 3.16.2.8769), then ran bundled `Contents/Resources/glm/zcode.cjs --version` and `--help` under a disposable HOME. CLI 0.17.0 advertises an `app-server` stdio entry and --resume. [Probe](evidence/zcode-darwin.json) records the actual app-server attempt; help text alone does not establish a working control session. The default CLI launch misses its bundled provider configuration location; the probe copies the app's shipped builtin configuration into a disposable directory and supplies explicit provider paths, leaving the installation untouched. The installed protocol uses strict NDJSON envelopes with id/method/params and rejects the JSON-RPC `jsonrpc` field. Removing that field makes runtime/capabilities succeed. session/create also requires handling the inbound session/requestRuntimePreferences callback; replying with optional enhancements, memory and automatic question resolution disabled makes creation and close succeed. Resume of the untouched closed session then returns Session not found. The separate persisted-turn fixture above succeeds after restart, so the empty-session result must not be generalized to conversational resume. See `pnpm probe:zcode`; other installations can set LAM_ZCODE_ENTRY and LAM_ZCODE_BUILTIN_CONFIG.
- WorkBuddy: Info.plist confirms bundle com.tencent.workbuddy.mac, desktop 5.8.3. Application resources include internal helper/guest SDK artifacts; their presence does not establish a supported public control API. No helper was invoked and no existing conversation was accessed. [Inventory evidence](evidence/workbuddy-inventory-darwin.json) hashes the installed guest SDK and records its browser-window guard, host invoke bridge and host-initialized MessagePort bootstrap. These are renderer transport internals, not a published standalone control-method contract. Reproduce with `pnpm probe:workbuddy:inventory`.
- WorkBuddy's official Open API documents OAuth-authorized local-assistant status/messages/history through its hosted service, plus cloud-task APIs. This is a documented integration candidate, not a verified direct LAN API. Requiring its cloud service would not meet the core no-mandatory-cloud architecture; retain it as an optional future route. The public connector docs establish outbound MCP, not GUI-session attachment.
